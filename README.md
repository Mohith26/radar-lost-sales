# Lost sales from floor gaps, for RADAR+ (concept demo)

**Live demo:** https://mohith26.github.io/radar-lost-sales/

RADAR knows, every few seconds, whether each size is on its home fixture, misplaced on another table or in a fitting room, sitting in the backroom, or gone from the store. That makes something possible that POS data alone can't do: price what each floor gap actually cost.

The catch is that sales are **censored**. A size only sells while it's on the fixture, so its sales history understates demand, and when it's missing some shoppers simply take the size next to it. Counting "hours out of stock x average sales rate" (the usual report) ignores that switching and overstates the loss.

This page, a new **Lost sales** tab under RADAR+ Analytics, estimates:

- real demand per SKU, using on-fixture time as exposure,
- the share of shoppers who take an adjacent size when theirs is missing (with a profile-likelihood interval),
- lost revenue per SKU and by cause (in backroom, misplaced, out of stock), with a bootstrap interval,
- what a faster backroom-to-floor response would recover.

Demo store (synthetic, 42 days, 33 styles x 5 sizes = 165 SKUs, 15-minute reads):

| | |
|---|---|
| Lost revenue, 6 weeks | **$15,918** (90% interval $13,324 to $17,702) |
| Share of shoppers who take the next size | 36% (95% CI 26% to 48%) |
| Lost while stock was in the backroom | 34% ($5,370) |
| Naive out-of-stock-hours estimate | $22,461, **41% too high** |
| Refill backroom gaps within 30 min | recovers $4,437 in 6 weeks (about $38.6k per store per year) |

The hidden truth for this store (never shown on the page) is $17,219, inside the interval.

## How it works

1. **Traffic index.** A day x hour-of-day multiplicative model fit to total store sales (iterative proportional fitting) gives the exposure of every 15-minute slot.
2. **Sufficient statistics.** For each style, slots are grouped by which of its 5 sizes are on the fixture (at most 32 patterns), summing traffic and per-size sales per day. The whole store compresses to a few thousand numbers.
3. **Censored demand with substitution.** Expected sales of size i in a pattern = traffic x [rate_i + theta x sum over missing neighbours k of rate_k / (number of k's neighbours on the fixture)], zero if i itself is off the fixture. Rates are fit by EM (the model is linear in the rates, so the updates are multiplicative); theta is profiled over a grid and its 95% interval is the set within 1.92 log-likelihood units of the maximum.
4. **Lost units.** For each SKU-slot off the fixture: rate x traffic x (1 - theta if a neighbour size is on the fixture, else 1), attributed to the cause RADAR recorded for that slot.
5. **Intervals.** Day-block bootstrap (60 draws): resample days, re-profile theta, refit rates, recompute losses, and add Poisson noise for the lost shoppers themselves so the interval targets the loss that actually happened.
6. **What-if.** Truncates each backroom gap at the chosen response time and counts the losses after it (first-order: demand and downstream stock held fixed).

## Validation

`scripts/validate.mjs` runs 30 more synthetic stores (true switching share varied 20% to 50%) where every lost shopper is known:

- average absolute error in lost revenue: **10%** (naive out-of-stock-hours estimate: 43%, biased +43%)
- average bias: -1.0%
- 90% intervals contained the truth in **83%** of stores (slightly under target; the 15-minute resolution misses sizes that sell out mid-slot)
- the switching-share interval contained the true value in 30 of 30 stores

```
node --test test/*.test.mjs        # 6 tests
node scripts/report.mjs            # numbers shown on the page
node scripts/validate.mjs 30 60    # regenerates data/validation.json (~1 min)
python3 -m http.server             # then open http://localhost:8000
```

Static HTML/CSS/JS with ES modules; no build step. Barlow and IBM Plex Mono from Google Fonts stand in for RADAR's GT Pressura and GT Pressura Mono; icons are Phosphor.

## Honest limitations

- **Synthetic data**, generated by my own simulator, so the model is close to well specified. Real stores add multi-size buyers, try-on diversion, color substitution, promotions and traffic counters that disagree with sales.
- Substitution only to adjacent sizes of the same style and color; switching to another color or style is not modeled.
- The traffic index is fit on total sales, which are themselves slightly depressed by gaps; a door counter would be better.
- The what-if ignores knock-on effects (a faster refill can empty the backroom sooner).
- No public screenshots of RADAR's apps or RADAR+ dashboards exist, so the UI follows RADAR's web design system (logo, orange, black, #f2f2f2, DIN-style type with a mono companion), not the real dashboard.

## Novelty

As of Nov 10, 2026, RADAR+ is described (launch July 2025, Feb 2026 expansion, June 2026 coverage) as offering try-on conversion, phantom inventory, misplaced-item alerts, replenishment priorities, 15-minute availability alerts, dwell time, on-floor availability and recovery time. I found no mention of censored-demand lost-sales estimation or size-substitution modeling. Nedap iD Cloud talks about lost sales and on-shelf availability qualitatively; I found no public substitution-aware estimate there either.
